# 题目评估：Rating、解法路径与人类反馈

本功能属于开发分支，尚未包含在 V2.2.1 的安装包或 V2.2.0 后端包中。需要同时使用本分支的 API、worker 与前端，并执行数据库迁移；仅换客户端不会新增服务端能力。

## 使用顺序

1. 在模型配置中保存生成、验证及审查模型。评估沿用这些配置：生成与验证模型分别盲解，审查模型比较解法与 KC。没有单独设置验证/审查模型时沿用已有配置，报告会标示模型来源，不能把同一模型的两次调用当作两种模型。
2. 从侧栏“题目评估”或编程题详情进入，选题后开始评估。后台任务可查看、取消；关闭页面不会取消任务。
3. 查看完整约束下的候选解法、知识组件、可能的绕过关系、错误路线、运行证据及未解决的分歧。候选 KC 不会自动进入正式知识点目录。
4. 在“锚点”中录入经过人工核对的历史题目、来源分数与抓取日期、题面/解法摘要、家族和适用人群。来源确认与人工审查人是必要条件。新实例没有预装的真值锚点或人类作答。
5. 发放评价邀请。每个现实评价者使用一个稳定编号；给同一人补发链接时复用该编号。设置作答窗口 T、练习/比赛情境及到期日。
6. 评价者打开独立页面，记录是否独立完成、何时使用帮助、尝试时间、卡点与实际解法。页面不展示参考分数、标准解、KC 分析或他人的评价。
7. 汇总反馈后，管理员查看复核材料，选择接受、修改、拒绝或暂缓并填写理由。**任何汇总都不会自动改正式分数。**

## 四种信息各自表示什么

| 信息 | 含义 |
|---|---|
| 目标难度 | 出题时设定的原有 difficulty，评级操作不覆盖它 |
| CF 风格参考区间 | 经审核锚点与可执行候选支持的比较结果，不是 Codeforces 官方评级或统计置信区间 |
| 人类观察 | 当前题目版本、特定人群和作答窗口下的分组结果；自报完成/能力不等于 OJ 核验 |
| 正式评级 | 管理员确认的值，带题目版本、证据快照、理由及决策历史 |

没有足够可比的已审核锚点、上下界矛盾、完整解法证据不足或争议未解时，系统不输出数值参考。初期至少需要三道不同家族的可比锚点及上下关系支持；执行时最多从审核锚点中取六道覆盖不同分数的题目，逐项判断可比性。

“30 个有效评价身份”只触发试点复核。重复提交相同内容不会增加人数或证据版本；实际修改保留修订历史。受助、见过原题、未开始、提前停止、观察不完整等情况分别处理；窗口之后完成不算窗口内成功。相同反馈快照重复汇总复用已有结果。

后续再评估会把当前题目版本中最多 12 条首次尝试的路线与卡点送入盲解后的 KC 分析，作为尚未核实的线索；每个文字字段最多 1000 字符，不附带评价身份字段、自报 CF 能力或主观分数。它们不会进入盲解，也不会因模型归类变成已核实的人类观察数。

当前没有共同锚点作答资料，不拟合 1PL/Rasch 模型，也不把主观打分平均成“实测 CF 分数”。能力未知和观察不完整不会被补成假数据。

## 搜索与组卷

按数字范围搜索、新建编程题组卷默认选择“正式评级”，仅采用仍有效的管理员确认值。可以明确切换为“目标难度”；不会用另一种分数悄悄补足数量。没有筛选数字范围的普通关键词搜索仍覆盖尚未评级的题目，目标值有明确标记。

旧 API 调用不传 `rating_basis` 时仍按目标难度处理，以兼容旧客户端。新字段只接受 `target` / `official`。未升级后端的客户端不能把旧搜索结果标为正式评级。

正式筛选会核验真实题目与测试版本。首期单次正式候选最多 200 道，超过时需要增加关键词、标签或缩小范围；不会截断后伪造完整结果数。测试摘要按对象版本缓存，读取大文件时使用流式 SHA-256，内容变更会失效。

保存组卷时再次检查决策与题目版本，并保存当时采用的正式评级快照。后续改分、改题集名称都不改写该历史。原有题集不会自动重排。

## 验证能证明到哪一步

- 两路盲解只接收题面、限制与样例，不接收目标分数、原标签、标准解或另一模型的回答。
- KC 分析在盲解之后进行；保留正确性论证、复杂度与适用范围。任一独立分析指出只适用部分约束，就不能因小测试通过提升为完整解法。
- 每次最多验证五条候选路径、32 条分层选取的冻结测试，单条输入/输出受传输预算约束。真实调用沙箱并保存运行身份与内容摘要；沙箱失败或回执不足显示“未执行/待复核”。
- 本期执行 C++ 与已支持的普通输出比较。特判题保持待复核，不用普通字符串比较替代 checker。
- 通过所选测试不等于正确性证明，也不证明某个 KC 绝对必要或已经被绕过。错误候选通过弱数据应作为质量疑点处理。
- 模型新提出的反例尚未独立验证输入合法性与标准输出，因此保留为待审候选，不计为实际击穿，也不自动写入正式测试集。
- 模型误导假设与人类实际报告分开保存；程序执行次数不增加人类样本量。

首次真实试点仍需核对锚点内容、收集人类数据并检验排序/误差与等待时间。单元测试、合成 HTTP/数据库测试和界面演示不证明真实评级准确率。

## 身份与部署

管理操作使用现有 JWT 的稳定用户身份与管理员角色；任意 `X-Actor` 头不能授予权限。邀请令牌只授权对应题目版本的评价任务，数据库只存摘要，可以撤销或过期；令牌本身不能证明现实人数，发放者仍需一人一个编号。

评价链接使用 URL 片段传递令牌，页面读取后移除片段，仅在当前会话保存。API 使用 `X-Qraft-Review-Token`，不接收 URL 查询参数中的令牌。Web 请求不携带内部 JWT；桌面代理还会隔离管理员 cookie，不让评价响应更改管理员会话。

显式开发模式下工作区仍沿用本地管理员身份，适合可信本机调试；这不是公网账号隔离。向不受信任的人开放服务前，须关闭开发模式并采用现有 JWT/网关授权。题目评估没有新增完整账号、多租户系统或自动公网部署。

后台任务若被 Temporal 超时/终止，查看或再次开始评估时会同步已经确认的终态。网络故障不会被当作任务失败；尚未创建的 pending 任务不会因一次查无记录被误杀，可通过明确取消释放。

## API

管理接口前缀为 `/api/v1`：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/rating/problems/:id` | 当前版本、报告、反馈统计、正式值与历史 |
| POST | `/rating/problems/:id/assessments` | 开始独立评估 |
| GET / DELETE | `/rating/assessments/:id` | 查询 / 取消 |
| GET / POST | `/rating/anchors` | 列出 / 新增人工审核锚点 |
| GET / POST | `/rating/problems/:id/invitations` | 列出 / 发放邀请；明文令牌只返回一次 |
| DELETE | `/rating/problems/:id/invitations/:invitation_id` | 撤销邀请 |
| GET | `/rating/problems/:id/feedback` | 查看本版本反馈 |
| POST | `/rating/problems/:id/calibration` | 固定快照并生成复核材料 |
| GET / POST | `/rating/problems/:id/decisions` | 查看历史 / 提交管理员决定 |
| GET / POST | `/public/rating/review` | 邀请令牌限定的题面 / 本人反馈 |

决定提交必须带当前题目 hash、反馈 hash 和当前正式决策 ID（无正式值时为空），并引用评估或汇总证据。实际接口字段以 `backend/internal/rating/types.go` 为准。过期或并发变更返回冲突，刷新证据后再确认，不自动覆盖。

研究依据、方案取舍与后续实测设计见 [设计说明](design/rating-kc.md)。
